01 — Les fondations

Frappe, ERPNext & toi

La toute première confusion à dissiper : Frappe et ERPNext ne sont pas la même chose. L'un est posé sur l'autre, et ton appli est posée sur les deux.

La techno · le framework
Frappe
Le moteur : serveur web, base de données, permissions, API REST, et une interface générée automatiquement. Python côté serveur, JavaScript côté navigateur. C'est le châssis + le moteur de la voiture.
Une grosse application faite AVEC Frappe
ERPNext
Comptabilité, stock, achats, ventes, RH… Une suite de gestion complète, construite avec Frappe. C'est un modèle de voiture fini.
TON application métier
hmd_agro
L'appli laitière : animaux, lactations, inséminations, vêlages, traites… Elle réutilise des briques d'ERPNext (le stock, les articles) et toute la puissance de Frappe. C'est ton aménagement sur-mesure.
≈ L'analogie Frappe = la techno. ERPNext = une appli déjà faite avec cette techno. hmd_agro = ton appli métier, qui s'appuie sur les deux. Quand quelqu'un dit « c'est du Frappe », il parle du framework ; quand il dit « on réutilise ERPNext », il parle des fonctions de gestion déjà prêtes.

L'idée géniale de Frappe tient en une phrase : tu décris tes données, et il génère le reste. Tu définis « un Animal a un nom, une catégorie, une date de naissance » et Frappe te fabrique tout seul le formulaire de saisie, la liste filtrable, l'API, la recherche et les permissions. Tu n'écris quasiment pas de « plomberie ».

Tu écris la description. Frappe écrit l'application.

02 — Le concept central

Le DocType, le cœur de tout

Si tu ne retiens qu'un seul mot, c'est celui-là. Dans Frappe, tout est un DocType. Un DocType, c'est trois choses réunies sous un seul nom :

  • une table dans la base de données ;
  • un formulaire pour saisir les données ;
  • un jeu de règles et de comportements.

Si tu connais Django ou Rails, c'est l'équivalent d'un « modèle » (Model). Sinon : imagine une fiche cartonnée bien rangée, dont Frappe gère automatiquement le classeur, la recherche et les droits d'accès.

Dans ton appli, chacun de ces éléments est un DocType :

hmd_agro/hmd_agro/doctype/
# Chaque dossier = un DocType = une table + un formulaire
animal/        lactation/     insemination/    velage/
traite/        avortement/    lot/             batiment/
pesee/         semence/       taureau/         alerte/
medicament/    traitement/    hmd_configuration/   …

Un Animal, concrètement, c'est une ligne dans la table tabAnimal. Une Lactation c'est une ligne dans tabLactation. Et Frappe te fournit gratuitement le formulaire pour les créer et les modifier.

✦ À retenir Quand tu veux ajouter une nouvelle « notion » à l'appli (par ex. « Bâtiment », « Ration »), la question est presque toujours : « quel DocType je crée, et quels champs il a ? »
03 — Sous le capot

Anatomie d'un DocType

Ouvre n'importe quel dossier de DocType : tu retrouves toujours la même poignée de fichiers. Voici ceux du dossier animal/, fichier par fichier.

animal.jsonLa définition. La liste des champs, leurs types, les permissions. Le cœur. C'est ce fichier que Frappe lit pour fabriquer la table et le formulaire.
animal.pyLa logique serveur (le « controller »). Une classe Python où tu mets tes validations et tes calculs. Tourne sur le serveur.
animal.jsLe comportement du formulaire, côté navigateur. Recalculs en direct, boutons, champs masqués. Tourne dans le navigateur.
animal_list.jsPersonnalise la vue liste (couleurs de statut, colonnes, filtres rapides).
test_animal.pyLes tests automatiques qui vérifient que la logique fait bien ce qu'on attend.

a) animal.json — la structure

Un fichier JSON qui décrit chaque champ (field). Un champ a un nom interne (fieldname), une étiquette affichée (label), et surtout un type (fieldtype).

animal.json (extrait simplifié)
{
  "doctype": "DocType",
  "name": "Animal",
  "fields": [
    { "fieldname":"nom",        "fieldtype":"Data",   "label":"Nom" },
    { "fieldname":"categorie",  "fieldtype":"Select", "options":"VELLE\nGENISSE\nVACHE" },
    { "fieldname":"date_naissance", "fieldtype":"Date" },
    { "fieldname":"mere",       "fieldtype":"Link",   "options":"Animal" }
  ]
}

Les types les plus courants : Data (texte court), Int / Float (nombres), Date, Select (liste de choix), Check (case à cocher), et le plus important pour les relations — Link.

✦ Le champ Link Un champ Link avec "options": "Animal" dit : « ce champ pointe vers un autre Animal ». C'est exactement une clé étrangère — la flèche entre deux tables dans ton MCD. Ici, mere relie un veau à sa mère.

b) animal.py — la logique serveur

C'est une classe Python. Le truc magique : Frappe appelle ses méthodes tout seul, à des moments précis de la vie d'un document. Tu n'as pas à les déclencher — tu remplis juste les « cases » que Frappe te tend.

animal.py — les « hooks » de cycle de vie
from frappe.model.document import Document

class Animal(Document):

    def validate(self):        # AVANT chaque sauvegarde — tes règles ici
        if self.date_naissance > frappe.utils.today():
            frappe.throw("La date de naissance ne peut pas être dans le futur")

    def on_update(self):       # APRÈS la sauvegarde
        ...

    def on_trash(self):        # AVANT la suppression
        ...

C'est précisément ici que vit ta logique métier. Exemple réel chez toi : quand on enregistre un Velage (vêlage), le code crée automatiquement l'Animal du veau, ouvre une Lactation et fait passer la mère de GENISSE à VACHE. Toute cette cascade vit dans ces méthodes.

c) animal.js — le formulaire vivant

Du JavaScript qui réagit dans le navigateur pendant la saisie : « quand l'utilisateur change ce champ, recalcule celui-là », ajouter un bouton, masquer une section.

animal.js
frappe.ui.form.on("Animal", {
    date_naissance(frm) {
        // recalcule l'âge dès que la date change, en direct
        if (frm.doc.date_naissance) {
            const jours = frappe.datetime.get_day_diff(
                frappe.datetime.now_date(), frm.doc.date_naissance);
            frm.set_value("age_jours", jours);
        }
    }
});
04 — La règle d'or

Serveur vs navigateur

C'est le point qui déroute tous les débutants. Le même DocType a du code à deux endroits — .py et .js — et ils ne tournent pas au même endroit ni dans le même but.

FichierOù ça tourneÀ quoi ça sert
.pySur le serveurLa source de vérité. Les validations sérieuses, celles qui protègent tes données.
.jsDans le navigateurLe confort. Aide la saisie, réactivité, ergonomie — mais ne protège rien.
! Attention — la faute classique Une validation mise uniquement dans le .js est contournable : quelqu'un peut écrire en base via l'API sans jamais passer par le navigateur. Si une règle doit toujours être vraie, elle va dans validate() du .py. Le .js, c'est du bonus.

Formule à graver : le .js rend la saisie agréable ; le .py rend les données fiables.

05 — Le fil de la vie

Le cycle de vie d'un document

Quand un utilisateur clique sur « Enregistrer », il ne se passe pas qu'une écriture en base. Frappe déroule une séquence, et t'invite à intervenir à chaque étape via les méthodes vues plus haut.

before_validate
Juste avant les contrôles. On prépare/nettoie des valeurs.
validate
Le grand contrôle. 99% de ta logique de règles métier est ici. Si une règle échoue, on appelle frappe.throw(...) et la sauvegarde est annulée.
before_save → écriture en base
Frappe écrit la ligne dans la table.
on_update
Après l'écriture. On déclenche les effets de bord : créer d'autres documents, mettre à jour un lié, envoyer une alerte.
on_trash
À la suppression. On vérifie qu'on a le droit de supprimer, on nettoie les documents liés.

Le cas particulier : la « soumission » (submit)

Certains DocTypes sont « soumissibles » (submittable). Ils ont alors trois états, pas deux :

  • Brouillon (Draft, 0) — modifiable librement.
  • Soumis (Submitted, 1) — validé, gelé. On ne peut plus le modifier normalement. C'est l'équivalent d'« officialiser » une pièce comptable ou un mouvement de stock.
  • Annulé (Cancelled, 2) — on défait un document soumis.

À ces transitions correspondent d'autres hooks : before_submit, on_submit, on_cancel. Dans le monde ERPNext, une écriture de stock ou une facture n'a d'effet réel qu'une fois soumise.

≈ L'analogie Brouillon = un formulaire au crayon, tu gommes autant que tu veux. Soumis = tu signes au stylo ; pour corriger, il faut officiellement annuler et refaire. Tout n'est pas soumissible — beaucoup de DocTypes vivent très bien en simple « enregistré ».
06 — Tout est relié

Les relations (ton MCD)

Ton diagramme conceptuel (MCD) n'est rien d'autre que la carte des champs Link entre tes DocTypes. Une flèche du MCD = un champ Link dans un .json.

les liens chez toi
Lactation   ──Link──▶ Animal      # une lactation appartient à une vache
Traite      ──Link──▶ Lactation   # une traite appartient à une lactation
Insemination──Link──▶ Animal      # + ──Link──▶ Semence
Velage      ──Link──▶ Animal      # crée de nouveaux Animal (les veaux)

Il existe aussi les « child tables » (tables enfants) : un tableau de lignes à l'intérieur d'un document parent. Chez toi, allotment_session_row est la table enfant de allotment_session — chaque ligne est rangée dans la session parente. Un enfant n'existe jamais seul, toujours porté par son parent.

✦ Lire une relation Pour savoir « à quoi est relié ce DocType », ouvre son .json et cherche tous les "fieldtype": "Link". Chaque options te donne la table visée. C'est ta façon la plus fiable de reconstruire le MCD depuis le code.
07 — Le câblage de l'app

Hooks, fixtures & patches

Au-dessus des DocTypes, quelques fichiers orchestrent l'ensemble. Ce sont eux que tu retrouves à la racine de hmd_agro/.

hooks.py — le plan de câblage

Le fichier de configuration central. Il dit à Frappe : « pour tel DocType, à tel événement, appelle telle fonction », branche les tâches planifiées (scheduler — par ex. « tous les jours, recalcule les alertes »), déclare les fixtures, etc.

hooks.py (extrait)
doc_events = {
    "Velage": {
        "on_submit": "hmd_agro.api.velage.creer_veaux_et_lactation",
    }
}

scheduler_events = {
    "daily": [ "hmd_agro.api.alertes.recalculer" ]
}

fixtures/ — les données livrées avec le code

Des données qui voyagent dans git avec l'appli : champs personnalisés, valeurs de configuration par défaut, rôles… Pour qu'en installant l'appli ailleurs, on retrouve la même base de réglages.

patches/ + patches.txt — les migrations

Des scripts qui modifient une base existante lors d'une mise à jour : « renommer ce champ », « recalculer cette colonne pour toutes les vieilles lignes ». patches.txt donne l'ordre d'exécution. Ils tournent quand on lance bench migrate.

hmd_configuration — les seuils, hors du code

Un DocType à toi qui range les paramètres métier (seuils d'alerte, jours de tarissement, bornes vert/orange/rouge des indicateurs) au lieu de les coder en dur. Très bonne pratique : on ajuste un réglage sans toucher au code.

✦ Le réflexe Un comportement « automatique » qui te surprend (un document créé tout seul, une alerte qui apparaît) ? Cherche d'abord dans hooks.py : c'est l'annuaire de tout ce qui se déclenche automatiquement.
08 — En pratique

bench & la console

bench est l'outil en ligne de commande de Frappe. Quelques commandes reviennent sans cesse :

terminal — les commandes du quotidien
$ bench start                       # lance le serveur de développement
$ bench --site monsite migrate       # applique les patches + maj des DocTypes
$ bench --site monsite console       # un shell Python connecté à ta base
$ bench build                        # recompile le JS / CSS
$ bench export-fixtures              # exporte les fixtures vers les fichiers

L'ORM : manipuler les données en Python

Dans la console (et partout dans les .py), tu parles à la base via l'ORM de Frappe — sans écrire de SQL. C'est cette même grammaire que tu vois dans tous tes controllers.

bench console
# Récupérer un document complet
animal = frappe.get_doc("Animal", "ANI-0001")
animal.nom            # accès à un champ

# Chercher une liste (avec filtres)
frappe.get_all("Animal",
    filters={"categorie": "VACHE"},
    fields=["name", "nom"])

# Créer un nouveau document
doc = frappe.new_doc("Animal")
doc.nom = "Marguerite"
doc.insert()
✦ Pour apprendre vite La bench console est ton meilleur terrain de jeu : tu peux interroger ta vraie base sans rien casser tant que tu lis (get_doc, get_all). C'est la façon la plus rapide de comprendre comment tes données sont reliées.
09 — La vue d'ensemble

Le modèle mental

Tout ce qu'on vient de voir tient dans un seul schéma. Garde-le en tête, le reste n'est que du détail.

la boucle Frappe
TU ÉCRIS
   animal.json  (structure)
 + animal.py    (règles serveur)
 + animal.js    (confort de saisie)
          │
          ▼
FRAPPE GÉNÈRE TOUT SEUL
   table SQL · formulaire · liste · filtres
 + API REST · permissions · recherche
          │
          ▼
LE CÂBLAGE RELIE LE TOUT
   hooks.py  déclenche les automatismes
   fixtures  livre les données de base
   patches   fait évoluer la base existante

Décris tes données, mets tes règles dans le .py, câble dans hooks.py. Frappe s'occupe du reste.
