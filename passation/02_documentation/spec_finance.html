00 · Mode d'emploi

00Comment lire ce document

Ce document est la spécification du module Finance. Il traduit le cadrage (plan_finance.html) et la consigne d'onboarding en unités buildables et testables : la liste des objets, le tableau « créer / étendre / configurer », les règles de gestion codifiées (RG / CF / RC), les flowcharts, et les user stories prêtes pour Jira — exactement les quatre livrables demandés.

L'idée maîtresse (rappel du cadrage) On ne réécrit pas de comptabilité : Vente, Dépense, Équipement, Intervention sont de l'ERPNext natif (Selling / Purchase Invoice / Journal Entry / Asset). Notre code se réduit à des Custom Fields, de la configuration et un peu de glue. Le point d'accroche existe déjà : chaque consommation poste un mouvement de stock — mais à coût zéro (basic_rate=0) ; la finance, c'est surtout brancher de vrais prix sur une mécanique de coûts déjà câblée.

Conventions de codification (maison)

  • RG-FIN-nn — règle de gestion (business rule).
  • CF-FIN-nn — contrainte fonctionnelle (invariant à préserver).
  • RC-FIN-nn — règle de calcul (formule d'indicateur).
  • ERR-<DT>-nn — code porté par un frappe.throw(...) ; avertissements en msgprint(indicator="orange", alert=True).
  • FIN-Snn — identifiant de user story (sert d'ancre Jira/commit).

Namespace -FIN- choisi pour ne pas entrer en collision avec les RG métier existants (repro/lactation). Vocabulaire français, indentation Python 4 espaces, jamais de valeur en dur (→ get_config() / Item Price).

Vérifié contre le code · 2026-06-29 Tous les champs et chemins fichier.json:ligne cités ont été confirmés contre le code (DocTypes, stock_utils, rapport_mensuel, hooks.py, boot.py, scripts setup/). Seule nuance relevée : le coût/litre (DT/L) est déjà calculé (rapport_mensuel.py:1293) ; il ne reste qu'à ajouter le DT/vache et à brancher la valorisation réelle (EPIC B). Le code reste la source de vérité.

07 · Exécution

07Backlog & séquencement

Ordre conseillé (détaillé dans plan_finance.html §06). On livre de la valeur tôt : le coût/litre arrive dès l'EPIC B.

  1. Phase 0 — Cadrage (bloquant). Dérouler le questionnaire plan_finance.html §04 (A→J) avec le gérant et le comptable. Sortie : document de décisions (référentiel, prix lait, niveau analytique, amortissements, date de bascule).
  2. EPIC A — FIN-S01, FIN-S02 (socle + analytique).
  3. EPIC B — FIN-S10 → S12 (quick win coût/litre).
  4. EPIC C — FIN-S20 → S23 (recettes).
  5. EPIC D — FIN-S30, S31 (immos).
  6. EPIC E — FIN-S40, S41 (charges & MO).
  7. EPIC F — FIN-S50, S51 (pilotage).
  8. EPIC G — FIN-S60, S61 (bascule & rôles, transverse).
Dépendances avant de coder
  • Accès au backup BD (données réelles) auprès de Sami — l'instance locale est vierge.
  • Repos clonés + dev container (ERPNext + hmd_agro via frappe_docker, cf. setup_guide.md partie A → http://hmd.localhost:8000).
  • Cadrage Phase 0 tranché : sans les décisions client, on hardcoderait des hypothèses — interdit (RG-FIN-01).

Méthode de travail (consigne onboarding) : une branche par sprint, jamais de push direct sur main, unit tests + validation CI + superviseur, commits au format référençant l'ID story (« FIN-S10 … »), suivi dans Jira.
